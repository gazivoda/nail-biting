# Lighthouse and installability (WS13)

Lighthouse 13.5 (`npx lighthouse`, fetched into the npx cache, nothing added to `package.json`) against the **real `server.js`
on a local port** (3213, scratch `DATA_DIR`), never against production. Performance, SEO, best practices and accessibility
for the marketing pages, mobile (Lighthouse's default simulated phone and 4x CPU slowdown on a slow 4G profile) and desktop
(`--preset=desktop`), three runs per cell, **median** reported.

Pages: `/`, `/how-it-works`, `/pricing`, `/about`, an existing compare page, a blog post, a WS11b feature page
(`/features/habit-reversal-coaching`, its flag `hrt_coaching` on) and the WS11a compare page (`/compare/hands-off`, its flag
`compare_competitors` on). The server ran with
`FEATURE_FLAGS=compare_competitors,hrt_coaching,urge_timer,phone_companion,share_links,event_sync,referrals,detection_behaviors,social_proof`
so that the flag-gated pages exist to be measured. The runner is `scripts/lighthouse/run.mjs`
(`node scripts/lighthouse/run.mjs --runs 3`), the numbers below are written into this file by
`node scripts/lighthouse/report.mjs` from `docs/agents/lighthouse-results/lighthouse.json`.

How to read the numbers: this is a lab run on a laptop that is also doing other work, served from `localhost` (no CDN, no TLS,
Google Analytics included), so read the performance score as a range, not a benchmark. The spread between the three runs is
printed. SEO, best-practices and accessibility are not load-sensitive.

## What the numbers say

- **SEO is 100 on every page and form factor, including the two flag-gated pages with their flags on. Accessibility is 100
  everywhere.** Best practices is 100 on every page except the home page (92-96 depending on the run) and an occasional blog run (see next point).
- **Best practices 96 on `/`: `errors-in-console` and `inspector-issues`.** The browser logs "Failed to load resource: 404
  `/auth/providers`" on every signed-out page load while no sign-in flag is on. This is designed behaviour (WS8:
  `server/routes/authProviders.js` answers 404 while all three sign-in flags are off, and `src/auth/providers.ts` treats
  404 as "no extra providers" and caches it), but a 404 on a fetch is always a red line in the console. **It is in
  production already (it came with push #1) and it costs 4 points of best practices on the home page.** Cheap fix if you want
  100: have the route answer `200 {"magic_link":false,"apple":false,"microsoft":false}` when no flag is on (that changes a
  documented "flagged route is 404 with the flag off" rule, so it is your call), or have the client skip the call when
  `/api/features` shows no sign-in flag on. Not changed here.
- **Mobile performance is 93-94 on the four main pages and 78 on the compare and feature pages** (LCP about 5.4 s in
  Lighthouse's simulated slow-phone conditions, TBT about 10 ms, CLS 0). Desktop is 97-100. The 78 is LCP, not JavaScript
  (I did not dig into which element it is). The two new pages perform exactly like the compare page that already existed (78 / 97), so the swarm did not
  make anything slower; the WS6 note ("first-visit 75, LCP 6.0 s on the phone view") is the same kind of number.
  **Update 2026-10-30 (home page, mobile, Lighthouse 13.6.0, 3 runs, medians, `/` served by the real `server.js`):**
  performance 92 to 94, **CLS 0.098 to 0**, TBT 4 to 3 ms, LCP 3.09 s to 3.09 s (unchanged within the run-to-run spread of about
  0.2 s). Checked with Lighthouse's applied throttling as well (`--throttling-method=devtools`): 86 to 89, LCP 3.03 s to 2.96 s,
  CLS 0.098 to 0. `/pricing` (100, LCP 0.9 s, CLS 0) and a blog post (80, LCP 5.4 s, CLS 0) did not move.
  What the home page's numbers were: the LCP element is the hero screenshot `<img>` (React creates it after the bundle has run).
  Its preload with `fetchpriority="high"` has been in the HTML since 55274aa, so "not discoverable" was not the problem. In real
  (unthrottled) time the page paints at about 70 ms; on the simulated slow phone the picture arrives long before the bundle does
  (applied throttling: picture at 2.1 s, `vendor` and `index` scripts at 2.8 s, first paint at 3.0 s), so **LCP is the JavaScript
  chain (about 185 KB gzipped), not the picture and not the 17 KB stylesheet** (the CSS is in by 1.8 s, before any script can run, so
  inlining it would not move LCP). The one thing the picture did cost was bytes sharing the pipe: a 412 px phone at 1.75x fetched
  the 1280 px file (28 KB) because `sizes` said `100vw` (84 px more than it is drawn) and no smaller file existed. There is now a
  640 px file (14 KB) and the right `sizes` (`shared/heroShot.js`, one constant for the `<img>` and both preloads), worth about 70 ms
  of applied-throttling LCP and 14 KB. The CLS was `useIsPhone` starting at `false` and flipping in an effect: on a phone the first
  frame showed "Start free trial" (200 px) and the next "Send the link to my computer" (full column), the "How it works" link
  wrapped under it and the screenshot and notes moved 60 px (`figure.relative`). It is now decided in the first render
  (`src/hooks/useIsPhone.ts`); the same swap is gone from every page with a full-size trial button. Lab numbers only, not a field
  (CrUX) claim. Not changed: the font preloads (74 KB, about a quarter of the bytes ahead of the scripts, but text painted in a
  fallback font and swapped later risks a layout shift; not tried), inlining the stylesheet, and moving the hero into the
  server HTML (the page is client-rendered, not hydrated).
- **The blog post is the one real performance problem: CLS 0.72 on mobile (0.75 desktop), performance 54 / 73.** The element
  that moves is the bottom call-to-action block (`div.sg-page` that starts "Catch your next bite."): the article body is
  rendered from `dist/posts/<slug>.json` after it is fetched, and the footer sits where the empty page ended, then is pushed
  down by about 10,000 px when the article arrives. A CLS above 0.1 is "poor" in Core Web Vitals and is what a search engine
  would see for blog traffic. **This is not from the swarm** (`BlogPost.tsx` and `usePost.ts` were last changed by the WS9
  trial-constant swap, a mechanical edit; the JSON-fetch design came from the earlier growth loops). Fix when you want it:
  reserve the article's height (the server already knows the word count) or render the first screen of the article from the
  server HTML, or do not render the footer block until the article is in. It was not touched here (it is not a small safe fix
  and not in WS13's scope).
  **Update 2026-10-30:** fixed by the last of those options (`BlogPost.tsx` no longer renders the footer while the article is
  loading; `src/pages/BlogPost.test.tsx`). Lab, mobile, 3 runs on two posts: CLS 0.719 to 0, performance 56 to 80. The post's LCP
  is unchanged at about 5.5 s on Lighthouse's simulated slow phone: the app's own h1 replaces the server-rendered one once the
  bundle and the JSON have arrived. That is the design (a client-rendered article over a server-rendered copy), not a bug to fix cheaply.
  **Update, same day (lane H):** it was fixable cheaply after all, see "Blog post LCP" below; the server copy never paints for a visitor with JavaScript.

## Blog post LCP (lane H, 2026-10-30)

Lab only, Lighthouse 13.6.0 mobile, one laptop with other lanes' work running (load average 4 to 6 on 14 cores), base = the
build of `bf6fdad`, head = this branch, the two builds served by their own `server.js` and measured alternately
(`node scripts/lighthouse/ab.mjs`). **These are lab numbers; nothing here is a field or Core Web Vitals measurement.**

**What the base LCP was.** The client-rendered h1 (`/blog/nail-biting-health-risks`) or lede paragraph
(`/blog/how-to-stop-nail-biting`), painted by React. The earlier "replaces the server-rendered h1" is not quite it: for a visitor
with JavaScript the server copy is `display:none` before the first paint (`html.js #ssr-page-content`), so it never paints.
The wait is a serial chain: HTML, then the entry bundle (82 KB gz) and vendor (101 KB gz), then the lazy BlogPost chunk (requested
only once the bundle has run), then `/posts/<slug>.json` (requested only after the chunk's first render and its effect).
Also in the chain: React 19 holds a Suspense reveal back until 300 ms after the fallback committed
(`FALLBACK_THROTTLE_MS = 300` in react-dom 19.2.4), so the chunk being there early did not help while the route stayed lazy.

**What changed.** (1) `/blog/<slug>` carries `<link rel="preload" as="fetch" crossorigin href="/posts/<slug>.json">`
(`server/marketing/postPreload.js`): one request, started at HTML parse, consumed by the page's own `fetch()` (checked in Chrome:
one request per visit, answered by the service worker from the second visit on, no "preloaded but not used" warning). (2) `BlogPost` is a static import in `App.tsx`: its chunk was 10 KB since the articles moved
to JSON, and lazy cost a request plus the 300 ms throttle (entry +9.6 KB raw, +2.4 KB gz). (3) recharts' own dependencies (redux
toolkit, immer, reselect, decimal.js-light, es-toolkit ...) matched no `manualChunks` rule and shipped in `vendor` to every page:
they are in `charts` now (vendor 100.9 to 75.1 KB gz). `scripts/blogPostPreload.test.mjs`, `scripts/bundleSplit.test.mjs`.

**LCP, medians (every run in the list, ms).** `sim` = Lighthouse's default simulated slow phone, 5 runs. `chrome` = the same phone
profile applied by Chrome itself (`--throttling-method=devtools`), 3 runs: slower to run, no modelling.

Performance score, sim (base to head): post 1 80 to 96, post 2 80 to 96, `/pricing` 100 to 100, `/` 92 to 93. Chrome-throttled:
84 to 92, 84 to 92, 91 to 92, 86 to 88. TBT 12 to 5 ms on the posts, unchanged on the controls (3 to 18 ms either way). CLS 0 on
both posts, `/pricing` 0, `/` 0.098 on both builds (not touched here). The sim number drops far more than the Chrome-throttled one
(minus 2.6 s against minus 0.74 s), and the reason matters when reading either:

- **Lighthouse's simulation puts `gtag.js` (178 KB, from the tag in `index.html`) on the LCP path whenever it finishes before the
  paint it observed.** In the base build the paint is at about 380 ms on the unthrottled run and gtag finishes at about 170 ms, so
  the modelled LCP carries a third-party download and its evaluation (5.4 s; with `--blocked-url-patterns=*googletagmanager*` the
  same base build scores 3.0 s, TBT 0, performance 95). With the preload and the static import the observed paint moves to about
  75 ms, before gtag finishes, and gtag leaves the modelled path. Chrome-throttled numbers do not have this effect.
- **The same switch flips on `/pricing` with no code change**: the base column holds 903 and 2854 in one set of five runs,
  depending on whether gtag finished near 160 ms or near 205 ms after navigation (internet latency to Google). A simulated LCP
  difference of about 2 s on one page can be that switch, so judge a change on the Chrome-throttled column and on many runs.
- Not done, in `index.html` (not this lane's file): start the gtag download later (for example on first interaction or after an
  idle timeout), since a 178 KB third-party script competes for the same slow link as the chunk and the JSON.

**Where the rest of the wait is.** About 2.7 s of the Chrome-throttled 2.77 s is the first paint of anything: a visitor with
JavaScript sees nothing until the entry bundle has been downloaded and run, because the article already in the HTML is hidden.
A prototype that left the server copy visible and mounted React with the article already in hand (no loading frame) measured
1.74 s Chrome-throttled LCP, with the server paragraph as the LCP element and CLS 0. It was **not shipped**: visitors would see a
plain-styled article that is replaced by the designed page when the bundle runs (a design call); the server copy's dark-mode text
colour (`prefers-color-scheme: dark`) is light on the page's always-light background, so it would have to go; and the swap
resets scroll to the top. The simulated score does not reward it.

## Installability (the PWA check)

Lighthouse 13 has **no PWA category** any more, so the installability check is Chrome's own, taken
over the DevTools protocol on a loaded page: `Page.getInstallabilityErrors` plus `Page.getAppManifest`. It returned **no
installability errors and no manifest errors**, with `phone_companion` off and on (table above). With it on, the manifest
(`server/routes/phone.js` answers `/manifest.webmanifest` while the flag is on) gains the two home-screen shortcuts ("I bit" and
"I feel an urge", `shortcuts: 2`); with it off it is the static manifest from the build. What this does **not** prove: that an
iPhone or an Android phone installs the app, how it looks on a home screen, offline behaviour of an installed copy or
the maskable icon on a real launcher (not testable here). The service worker does install over plain-http localhost only if the
`upgrade-insecure-requests` directive is removed (see `privacy-audit-report.md`, "A finding about local testing"); the
installability check passes without it because Chrome's check does not need the worker to be active.

## Re-running

```
npm run build:web
node scripts/lighthouse/run.mjs --runs 3          # about 15 minutes; or --only /pricing,/about
node scripts/lighthouse/report.mjs                # rewrites the Results section above
# two builds side by side (a base checkout and this one), same pages, alternating runs:
node scripts/lighthouse/ab.mjs --base /path/to/base-checkout --head . --pages /blog/nail-biting-health-risks,/pricing --runs 5
node scripts/lighthouse/ab.mjs ... --devtools     # throttle in Chrome instead of the simulation
```
Run it alone: another browser or a build running at the same time moves the performance scores by several points.
